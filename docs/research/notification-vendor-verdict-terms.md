# Knock commercial fit for the vendor decision

Accessed **2026-11-16**, using public primary sources. This refresh supports [the vendor decision](https://github.com/bzhang-coke/cohort-005-project/issues/18). Current constraints supplied for this review: Cadence owns preferences and the custom UI; all vendor requests pass through Cadence's server. Knock remains eligible despite lacking a provider hard stop, with a fake by default, an opt-in allowlisted live path, a conservative application cap, monitoring, and **written overage clarification before live use**. A small unobtrusive attribution link is acceptable **if sufficient**. No paid plan is authorized. No account, vendor contact, or live service call was used.

**Assessment:** Knock remains a plausible conditional choice for this architecture. The required API capabilities appear available on Free. Public documentation still does not settle the exact custom-feed attribution obligation or Free-overage treatment. Successful integration tests cannot resolve those commercial questions.

**Documented facts**

| Subject | Current evidence |
| --- | --- |
| Free entitlement | $0; no card required; 10,000 delivered messages/month; Feed API, custom components, API/CLI management, and unlimited feed retention included. Branding removal is excluded. Starter is $250/month, includes 50,000 messages, then $0.005/message, and includes branding removal. [Pricing](https://knock.app/pricing) |
| Server access | Secret API keys can perform any API request and are scoped to an environment. The feed endpoint returns items and counts through ordinary HTTP requests. The documentation does not make a browser SDK a prerequisite for these APIs. [Authentication](https://docs.knock.app/api-reference/overview/authentication), [feed API](https://docs.knock.app/api-reference/users/feeds) |
| Development usage | A successful delivery to one recipient on one channel counts. Usage accrues across environments. In-app feeds cannot use sandbox mode; channel conditions can restrict test recipients, but allowed deliveries still count. [Plans and usage](https://docs.knock.app/manage-your-account/knock-plans) |
| History versus logs | Free message/workflow logs have 30-day retention; feed items remain fetchable indefinitely and support status updates afterward. The retention guide says custom retention policies are unsupported, while pricing describes feed retention as configurable. A particular automatic expiry/deletion policy is therefore not established by these pages. [Retention guide](https://docs.knock.app/manage-your-account/data-retention), [pricing](https://knock.app/pricing) |
| Deletion | The user-delete API permanently deletes the user and associated data. Account owners can delete an account through the dashboard; the instructions specify removal after 24 hours and immediate revocation of keys. Neither page labels deletion a paid feature. [User deletion](https://docs.knock.app/api-reference/users/delete), [account deletion](https://docs.knock.app/manage-your-account/account-deletion) |
| Usage visibility | `GET /v1/billing/summary` exposes a draft-invoice snapshot, per-metric quantities, billing-period boundaries, and amount due; its plan schema includes `free`. The documented limit is one request/second. No paid gate, freshness guarantee, or spend-control operation is specified on this endpoint. [Billing API](https://docs.knock.app/mapi-reference/billing/retrieve_summary) |

**Unresolved commercial terms**

1. **The accepted attribution link is not yet an established Free-plan condition.** Feed settings expose `features.branding_required`; account features expose `knock_branding_required`. These explicitly describe a display requirement. The custom-feed guide demonstrates custom UI, but the reviewed pricing, guide, API descriptions, and Terms do not specify the required wording, link, logo, size, placement, or exemption for server-mediated requests. Obtain a written answer stating whether a small unobtrusive link is sufficient for a wholly custom Cadence feed with no Knock browser SDK, and precisely what must be displayed and where. Do not infer permission to omit branding from SDK choice or custom-component availability. [Feed settings](https://docs.knock.app/api-reference/users/feeds/get_settings), [account features](https://docs.knock.app/mapi-reference/auth/verify), [headless guide](https://docs.knock.app/in-app-ui/react/headless/feed), [Terms](https://knock.app/legal/terms-of-service)

2. **Free has no vendor-enforced spending boundary established here.** The pricing FAQ says messages are not hard-capped and that Knock contacts over-limit customers about a payment method for the next month. The Terms, dated March 4, 2026, say exceeding Free entails fees for usage in that billing period. Neither establishes the exact Free-overage calculation or an unconditional no-charge grace period. Request written clarification of the first over-limit period's rate/base charge, any grace or explicit upgrade requirement, the allowance reset boundary, and whether an account-level hard stop is available. Billing-API visibility does not reconcile the fee language. This is a documentation gap, not a conclusion about contractual enforceability. [Pricing FAQ](https://knock.app/pricing#frequently-asked-questions), [Terms—Fees](https://knock.app/legal/terms-of-service), [billing API](https://docs.knock.app/mapi-reference/billing/retrieve_summary)

**Inference and decision recommendation**

The server gateway is technically compatible with the documented authentication/API model. It does not change commercial obligations. The agreed local cap should govern sends before submission, with conservative allowance for recipient fan-out, retries, and usage outside the gateway; a periodically fetched invoice cannot serve as the sole cutoff. After the accepted clarification gate is satisfied, verify the billing endpoint's availability and update lag during live development testing. This is an implementation inference from the metering and snapshot semantics above, not a vendor zero-cost guarantee.

The **final vendor verdict remains a human decision**. Recommend keeping Knock eligible with the accepted development safeguards, subject to satisfactory written attribution clarification and the agreed overage clarification before live use. Any branding answer exceeding the small-link condition needs a new human decision. These clarifications are needed to claim the commercial questions are resolved; another account or UI experiment cannot provide them. Any paid plan remains a separate, unapproved decision.
