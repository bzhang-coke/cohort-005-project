**Recommendation:** these APIs establish a credible implementation path without provisioning an account now. Defer authenticated runtime checks to implementation. Do not treat `markAllAsRead()` as proof of the agreed concurrency behavior: timestamp-filtered REST is the stronger planning basis. The action boundary, asynchronous feedback, reconciliation, retention policy, and account switching remain under [How should Cadence produce, store, and deliver its Notifications?](https://github.com/bzhang-coke/cohort-005-project/issues/17). ## Mark all read: documented path and exact uncertainty

`POST /v1/channels/{channel_id}/messages/bulk/read` accepts `recipient_ids`, `older_than` (messages inserted **before** that timestamp), archived/engagement filters, and optional tenant/workflow/data filters. It returns an asynchronous operation, not completion of every mutation. Scope the request to the current person and intended channel, retaining any deliberate tenant scope; avoid accidentally limiting it to loaded IDs. [Bulk status endpoint](https://docs.knock.app/api-reference/channels/bulk/update_message_status)

`GET /v1/bulk_operations/{id}` exposes status, processed counts, errors and completion. Its estimates can differ from processed counts. This endpoint is absent from the documented public-key allowlist: plan server-side polling unless public access is separately verified. [Bulk operation API](https://docs.knock.app/api-reference/bulk_operations/get), [public-key endpoints](https://docs.knock.app/in-app-ui/security-and-authentication#public-api-key-endpoints)

Source inspection at [`knocklabs/javascript` commit `81b9db8`](https://github.com/knocklabs/javascript/tree/81b9db8f0f8dc1f2a9af7bd110917845034b7f03) finds:

- `markAllAsRead()` optimistically sets unread count to zero, then invokes bulk status change. The source explicitly notes a race with incoming messages while the bulk operation is pending. Its request builder passes user/status/archive/tenant/data scope, **no time cutoff**. [Feed implementation](https://github.com/knocklabs/javascript/blob/81b9db8f0f8dc1f2a9af7bd110917845034b7f03/packages/client/src/clients/feed/feed.ts#L268)
- The browser SDK's bulk options type omits `older_than` and uses `user_ids`; the REST reference uses `recipient_ids`. Therefore the documented REST request, or a verified server SDK binding, is the planning path; do not assume the browser helper exposes the needed typed option. [Browser types](https://github.com/knocklabs/javascript/blob/81b9db8f0f8dc1f2a9af7bd110917845034b7f03/packages/client/src/clients/messages/interfaces.ts), [REST schema](https://docs.knock.app/api-reference/channels/bulk/update_message_status)

**Inference:** fixing a timestamp `T` once and supplying `older_than=T` prevents messages inserted at/after `T` from matching the documented predicate, even if processing finishes later. However, that predicate describes provider insertion time, not browser receipt time. An already-created notification delivered late to the browser can fall before `T`. The docs do not specify atomic snapshot behavior, concurrent read/unread conflict ordering, clock-skew handling, a server-issued click boundary, or maximum completion latency. [Timestamp predicate](https://docs.knock.app/api-reference/channels/bulk/update_message_status), [deferred operation](https://docs.knock.app/in-app-ui/javascript/sdk/feed-client), [real-time events may be throttled](https://docs.knock.app/in-app-ui/api-overview#real-time-delivery)

The bulk reference carries a retention-policy notice; the retention guide preserves old feed retrieval and status updates without specifically naming bulk processing. Do not equate unlimited storage with a verified unlimited-age bulk scan. An alternative is to paginate with a fixed insertion cutoff, collect IDs, then call explicit-ID batch read; these primitives support bounded historical updates without promising a transactional snapshot. Choose the implementation during integration planning. [Retention exception](https://docs.knock.app/manage-your-account/data-retention#message-log-data-retention-details), [feed filters](https://docs.knock.app/api-reference/users/feeds), [batch status API](https://docs.knock.app/api-reference/messages)

These are precise design/contract limits, not evidence that signup is needed now. A small live test could expose a defect but could not prove universal concurrency or long-age behavior. If strict browser-arrival ordering or an atomic cross-history operation becomes mandatory, seek an explicit vendor contract or use app-owned ordering/state; a signup alone would not answer that requirement.

## Authentication and identity switching

Enhanced security is off by default and must be enabled. It then requires a backend-signed RS256 user JWT with `sub`; include expiry. Explicit resource grants can restrict feed and preference access. Tokens can refresh before expiry, and re-authentication restarts the real-time connection. These are documented security mechanisms, not evidence that Cadence has configured them correctly. [Authentication](https://docs.knock.app/in-app-ui/security-and-authentication)

The inspected client tears down connections when credentials change; `logout()` clears local credentials/connections. This is not a remote JWT revocation call. No individual signed-user-token revocation API was located in the authentication reference; do not promise that switching Cadence users invalidates an already-copied token immediately. Token expiry, refresh authorization, request races and emptying old UI state belong in the integration design and tests. [Client implementation](https://github.com/knocklabs/javascript/blob/81b9db8f0f8dc1f2a9af7bd110917845034b7f03/packages/client/src/knock.ts#L107), [authentication reference](https://docs.knock.app/in-app-ui/security-and-authentication)

## Compatibility and verification boundary

Cadence declares React 19.2.7 and React Router 8.3.0 with SSR enabled; DevUI posts a numeric user ID to a session-cookie action and redirects. [Dependencies](../../package.json), [SSR](../../react-router.config.ts), [DevUI](../../app/components/dev-ui.tsx), [switch action](../../app/routes/api.switch-user.ts), [session](../../app/lib/session.ts)

The inspected Knock React package declares React/ReactDOM 19 support and ESM/CJS exports; its Next/TanStack peers are optional, not React Router requirements. Provider and feed hooks expose lifecycle handling. This supports plausibility, not a claim that this checkout is a published release or that Cadence SSR/hydration passes. An isolated pinned-package import/typecheck/SSR test with mocked transport needs no vendor account. [Package declarations](https://github.com/knocklabs/javascript/blob/81b9db8f0f8dc1f2a9af7bd110917845034b7f03/packages/react/package.json), [provider](https://github.com/knocklabs/javascript/blob/81b9db8f0f8dc1f2a9af7bd110917845034b7f03/packages/react-core/src/modules/core/context/KnockProvider.tsx), [feed hook](https://github.com/knocklabs/javascript/blob/81b9db8f0f8dc1f2a9af7bd110917845034b7f03/packages/react-core/src/modules/feed/hooks/useNotifications.ts)

During implementation, use two recipients and more than one page of history to check persistence after reload, separate seen/read state, timestamp-bounded mark-all completion with concurrent inserts, refresh/error reconciliation, forged/expired/missing-token rejection, and rapid DevUI switching with delayed responses. This is proposed runtime validation, not a pre-commitment signup requirement or a completed test. Batch/bulk deduplication can even return success with some entities unchanged and a rate-limit header, so success status alone is insufficient. [Rate-limit semantics](https://docs.knock.app/api-reference/overview#batch-and-bulk-endpoint-deduplication-rate-limits)

No application checks were run because this artifact changes no `app/` files. Free-plan attribution is a separate commercial evidence question; this API note does not establish an exemption for a custom feed.
