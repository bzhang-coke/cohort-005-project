# Knock integration boundary evidence

Accessed **2026-11-16** for [integration planning](https://github.com/bzhang-coke/cohort-005-project/issues/17). Follows [the API verdict](notification-vendor-verdict-api.md). Public documentation, published OpenAPI schemas, and official SDK source only; no signup, credentials, live test, or application change. Commercial gates still apply before live use.

**Finding:** a user-marker update can supply a documented Knock-generated timestamp, but its use as an exact feed-insertion boundary needs an explicit integration assumption. Insertion filters have positive documentation support for unread counts. No published mechanism was found for advancing Knock's clock or creating genuinely aged feed fixtures.

## Provider-derived read-all cutoff

**Documented:** the feed response contains `entries`, `meta`, `page_info`, and `vars`; neither it nor `PageInfo` exposes a current timestamp or snapshot token. The reviewed public and Management API paths expose no clock endpoint. An item's timestamp describes that item's creation, not the time of the query. No provider-clock contract for HTTP `Date` was found. [Feed reference](https://docs.knock.app/api-reference/users/feeds/list_items), [API schema](https://docs.knock.app/openapi.json), [Management schema](https://docs.knock.app/mapi/openapi.json)

**User-marker candidate:** `PUT /v1/users/{user_id}` merges supplied properties and returns a `User`, including required `updated_at`. The user guide defines that field as “The last time we updated the user”; `created_at`, in contrast, comes from the caller. A server-only custom marker therefore has a credible path to a provider-generated update timestamp. [Identify endpoint](https://docs.knock.app/api-reference/users#identify-user), [user object](https://docs.knock.app/concepts/users#the-user-object), [custom properties](https://docs.knock.app/managing-recipients/identifying-recipients#custom-properties)

**Implementation inference:** persist the local command, write a fresh marker nonce, validate the returned identity/marker/timestamp, and persist its exact `updated_at` as `T` before submitting read-all. Send only Cadence-owned fields, never a caller-provided `updated_at`. A lost marker response can restart setup with a fresh nonce while no read mutation has begun; once `T` is persisted, every read retry must retain it. This defines a boundary at provider marker processing, which occurs after the person's click. It is not a documented click-time snapshot.

**Unestablished:** `IdentifyUserRequest` permits additional properties; `updated_at` is not an explicitly writable request property, but the schemas do not mark it read-only or specify collision handling with custom properties. The docs do not promise that an unchanged upsert advances the timestamp, nor specify clock synchronization, monotonicity, precision, or ordering between user updates and message/feed insertion. Those omissions prevent claiming a fully documented ordering guarantee. [User schemas](https://docs.knock.app/openapi.json), [recipient properties](https://docs.knock.app/managing-recipients/identifying-recipients#reserved-properties)

**Alternative timestamp source:** `POST /v1/objects/{collection}/bulk/set` with one Cadence-only object returns a `BulkOperation`; its `inserted_at` records operation creation. An isolated collection without workflow references or subscriptions provides a non-notification mutation candidate. This avoids using a user's mutable timestamp, but still lacks the cross-resource ordering contract above. Do not assume that an empty bulk input is accepted merely because the schema has no minimum length. [Bulk set objects](https://docs.knock.app/api-reference/objects/bulk/set), [operation timestamp](https://docs.knock.app/api-reference/bulk_operations/schemas/bulk_operation)

**Message/feed relationship:** Knock describes the Feeds API as a specialized view of messages delivered to an in-app channel. The feed guide describes `inserted_at` as message-generation time; bulk `older_than=T` selects messages inserted strictly before `T`. This supports the interpretation that both refer to the same logical message, but does not explicitly establish timestamp equality across representations or behavior when message creation precedes delayed feed delivery. Do not substitute event time or trigger acceptance time. Preserve the returned timestamp's precision; equal timestamps are outside the documented strict bulk predicate. [Message model](https://docs.knock.app/concepts/messages), [feed timestamps](https://docs.knock.app/in-app-ui/api-overview#feeditem), [bulk predicate](https://docs.knock.app/api-reference/channels/bulk/update_message_status)

## Lost bulk-read response

**Documented limit:** the bulk-operation reference exposes only `GET /v1/bulk_operations/{id}`. No operation list, recipient/metadata search, or cancellation endpoint was found in either published API schema. The bulk-read request has message-selection filters, but no caller-supplied operation ID or correlation metadata. Its `trigger_data` filters existing messages; it does not label the job. `Idempotency-Key` is explicitly effective only on workflow triggers, so it cannot recover a lost bulk-read response by replay. [Operation API](https://docs.knock.app/api-reference/bulk_operations), [bulk request](https://docs.knock.app/api-reference/channels/bulk/update_message_status), [idempotency scope](https://docs.knock.app/api-reference/overview#idempotent-requests), [API schema](https://docs.knock.app/openapi.json), [Management schema](https://docs.knock.app/mapi/openapi.json)

**Recovery implication:** if Knock may have accepted a bulk read but Cadence lost its ID, these APIs cannot establish that every possibly accepted job is terminal. A later retry finishing, or a feed reconciliation showing all matching items read, does not prove the unidentified job can no longer mutate them. Preserve `T` and the ambiguity; do not treat either observation as sufficient evidence to release a mark-unread lock. A vendor-assisted resolution or separately established completion guarantee would be needed. No maximum job lifetime was established in the reviewed contract.

**Explicit-ID alternative:** `POST /v1/messages/batch/read` accepts `message_ids`; its documented `200` response is an array of updated `Message` records, including read state, rather than a `BulkOperation`. Neither the endpoint documentation nor `BatchMessagesStatusRequest` specifies a maximum batch size (`maxItems` is absent); a chosen chunk size remains an implementation choice to verify. [Batch read](https://docs.knock.app/api-reference/messages/batch/mark_as_read), [request/response schema](https://docs.knock.app/openapi.json). A successful HTTP response can still contain unchanged entities subject to deduplication limits: inspect `x-ratelimited-{param}`, returned IDs and read state, then reconcile. `Idempotency-Key` is ineffective here too. [Rate-limit and idempotency rules](https://docs.knock.app/api-reference/overview#batch-and-bulk-endpoint-deduplication-rate-limits). **Inference:** enumerating feed IDs at fixed `T` and tracking these request/response batches avoids asynchronous bulk-job discovery on the acknowledged path. It does not establish atomic multi-page selection, all-or-nothing updates, cancellation on timeout, or a maximum server execution time. A lost response still leaves a potentially executing mutation; reconciliation or a successful retry alone does not establish that the original request has stopped.

## Ninety-day visible history and unread count

**Documented support:** the filtering guide says filters affect feed results and unseen/unread badge counts, then directs readers to the API for all options. The official client includes `inserted_at_date_range` in `FeedClientOptions`, maps it to `inserted_at.gt/gte/lt/lte`, and uses the returned `meta` directly. This is stronger than assuming that counts follow filters merely because both appear in one response. [Filtering guide](https://docs.knock.app/in-app-ui/feeds/filtering-in-app-feeds), [options](https://github.com/knocklabs/javascript/blob/81b9db8f0f8dc1f2a9af7bd110917845034b7f03/packages/client/src/clients/feed/interfaces.ts#L19), [query conversion](https://github.com/knocklabs/javascript/blob/81b9db8f0f8dc1f2a9af7bd110917845034b7f03/packages/client/src/clients/feed/utils.ts#L34), [metadata handling](https://github.com/knocklabs/javascript/blob/81b9db8f0f8dc1f2a9af7bd110917845034b7f03/packages/client/src/clients/feed/feed.ts#L599)

**Inference and finite check:** applying the same `inserted_at` lower bound to every feed/count request can hide expired entries and exclude them from the badge while deletion is delayed. Verify this with a few real items on both sides of a recent cutoff, comparing filtered metadata with an enumerated result. Include an item exactly on the cutoff and read/unread states. The guide has no insertion-filter-specific count example or atomic count/page snapshot guarantee. Cadence must advance the bound and expire already-loaded UI entries; an old fetched response cannot implement immediate age expiry by itself. Filtering does not delete provider data.

## Testing old history without waiting months

**Documented tools:** workflow tests can edit input data, skip delay steps, and suppress downstream delivery in sandbox mode. None is documented as changing provider insertion time. The trigger/run request schemas offer no backdated insertion argument; the reviewed API paths and documentation index expose no feed-history import or test-clock API. This is a bounded search finding, not proof that vendor-assisted fixtures are unavailable. Feed content/metadata is immutable after generation except for engagement state. [Workflow testing](https://docs.knock.app/send-notifications/testing-workflows), [trigger contract](https://docs.knock.app/api-reference/workflows/trigger), [run contract](https://docs.knock.app/mapi-reference/workflows/run), [documentation index](https://docs.knock.app/llms.txt), [feed immutability](https://docs.knock.app/integrations/in-app/feeds#frequently-asked-questions)

Proposed finite verification layers:

| Layer | What it establishes | Limit |
| --- | --- | --- |
| Fake provider fixtures at 31, 89, 90, and 91 days, with multiple pages and equal timestamps | Cadence's cutoff calculation, pagination, status requests, immediate visibility/count exclusion, and purge retry/deadline logic | Does not exercise aged Knock storage |
| Fresh live entries separated by a short test cutoff | Actual insertion filters/counts, marker response, bulk read/delete, concurrency, reconciliation, and accelerated cleanup behavior | A short test retention period does not exercise Knock's diagnostic-log aging path |
| Published old-age contract | Feed retrieval/status changes remain available after diagnostic-log expiry; the bulk schema explicitly permits indefinite in-app updates | Contract evidence, not a completed aged-service test |
| Vendor-provided pre-aged fixture or already-aged test tenant, if actual age is a release gate | Behavior after provider retention transitions | Availability must be confirmed; no public self-service method was found |

The third layer is supported by [retention documentation](https://docs.knock.app/manage-your-account/data-retention#message-log-data-retention-details) and `BulkUpdateMessagesForChannelRequest.description` in the [API schema](https://docs.knock.app/openapi.json). Changing a business-event date inside trigger `data` cannot stand in for any aged-provider layer.
